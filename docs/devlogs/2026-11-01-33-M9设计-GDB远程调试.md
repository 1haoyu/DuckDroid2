## 0. 一句话

用一份 RSP 服务端，把 Binary Ninja / gdb / lldb 接到模拟器上；
**只做"调试驱动"模型**（runner 起来后停在入口，由客户端 `continue`），
不做附加到运行中实例、不做信号投递、不做源码级调试。

调试面和 M8 的指令级 trace 同一形态：**默认不编译**，
`-DDUCKEMU_ENABLE_DEBUG=ON` 才编入；运行时再加 `--debug` 才监听。
生产构建里没有 RSP 代码，链接期就不可用。

## 1. 范围

### 做

1. **RSP 子集**：连接、寄存器、内存、断点、watchpoint、单步、线程、模块。
2. **模型 A（调试驱动）**：runner 加 `--debug [PORT]`（默认 31337），
   实例加载完目标后停在入口，客户端连上继续。一次调试会话 = 一次目标调用。
   `--debug` 只在 `DUCKEMU_ENABLE_DEBUG=ON` 的构建里存在；默认构建根本不带。
3. **Z0 断点**落在目标模块任意指令地址；**thunk 断点**落在导入符号/ JNI 表项
   （`0x70000000 + 8 * index`）上，命中时带符号名。
4. **Z2/Z3/Z4 watchpoint**：走 `UC_HOOK_MEM_*`，数量不限（比硬件调试寄存器强）。
5. **单步**：Unicorn 的指令计数，不装 per-instruction hook。
6. 客户端验收：**Binary Ninja 内置 GDB RSP adapter** 能连、能看反汇编、能下断点、
   能单步、能看内存；`gdb-multiarch` 作为回归客户端。

### 不做

- `gdbserver --multi` 调试服务器模式（BN 本身也不支持）。
- **附加/中断任意正在运行的实例**（模型 B）。那要处理"停在嵌套 guest 帧里再继续"，
  见 §3.3。
- 信号投递。信号面仍是 no-op；只把 fault 映射成 stop reason 上报。
- 反向执行、DWARF/源码级调试、调用栈展开（沿用 M8：x29 链很浅）。
- NEON/Q/D/S 向量寄存器、FPU（与 M8 一致，aarch64 core 之外的寄存器先不报）。
- 穿过 Worker / System 暴露。**RSP 只存在于 runner 进程，只绑 `127.0.0.1`。**
- 默认构建包含调试面（同 trace：不显式开选项就不编）。
- 修改目标 `.so`、inline hook、trampoline。

## 2. 客户端事实（决定了验收标准）

| 客户端 | RSP 支持 | 结论 |
|---|---|---|
| Binary Ninja | 内置 `GDB RSP` adapter：`Debugger → Connect to Remote Process` | **验收客户端**。面向 gdbserver 写的，遇到未实现包会退化或报错，包日志是最好的说明书 |
| gdb / lldb | 原生 | 回归客户端；`gdb-multiarch` + `set debug remote 1` 可当抓包工具 |
| IDA | `Remote GDB Debugger`，官方只列 x86/ARM/MIPS/PowerPC | aarch64 不在官方列表；社区用 QEMU aarch64 stub 连过，能用但不保证。**不作为验收标准** |

两条硬事实直接影响设计：

1. **BN 把普通 gdbserver 当"远程进程"**，连接是"一次性"的，目标退出即断开。
   这正好等于模型 A：一个实例一个端口，目标函数返回后会话结束。
2. **BN 不支持 `--multi`**，所以不需要实现 `qRcmd` 的 `vRun`、`QNonStop`、
   进程枚举这一类服务器模式包。

## 3. 关键设计决策

### 3.1 模型 A：runner 是调用方，调试器是控制方

现有 runner 的形状（`code/user_code/<case>/main.cpp`）：

```cpp
auto instance = RuntimeInstance::create(config);
instance->loadLibrary(so);
instance->callFunction(entry, args);   // 宿主线程阻塞到 guest 返回
```

M9 只插两处，而且只在 `--debug` 时生效：

```cpp
auto instance = RuntimeInstance::create(config);
instance->loadLibrary(so);
// --debug [PORT]：默认构建里这个调用返回 Unsupported（stub 实现）；
// 只有 -DDUCKEMU_ENABLE_DEBUG=ON 的构建才会真的创建监听。
if (debug_enabled) {
    auto debug = instance->startDebugServer({ .port = port });   // 新增
}
auto result = instance->callFunction(entry, args);               // 不变
```

`--debug` 的形态跟 `--trace DIR` 一致，端口可选，默认 `31337`。
未传 `--debug` 时连 socket 都不创建；未用 `DUCKEMU_ENABLE_DEBUG=ON` 编译时，
`startDebugServer` 返回 `Unsupported` 并说明重编开关（同 `insn_trace_stub.cpp`）。

时序：

```text
runner 宿主线程            guest 主线程              RSP 客户端(BN)
      |  startDebugServer |                            |
      |------------------>| listen(127.0.0.1:port)     |
      |  callFunction     |                            |
      |------------------>| entry 断点命中 -> park     |
      |                   | accept / 包循环 <----------|
      |                   |   g/m/M/Z0/s/c ...         |
      |                   | continue -> 重新进入 run() |
      |<------------------| 返回 / 退出                |
```

`callFunction` 本来就阻塞到 guest 返回，所以 runner 的调用流程一行不用改；
调试面只是多了一个"谁来驱动它跑"的闸门。

### 3.2 谁在跑 RSP 循环：停在 park 点的那个 guest 宿主线程

**不引入跨线程访问 engine。** guest 线程停住时，它在 `hostThreadLoop` 里、
持有实例执行锁（`execution_mutex_`），此时它自己跑 RSP 的收包-回包循环：

```
uc_emu_start 返回
  -> handleRunOutcome：这是 debug stop 吗？
  -> 是：park（不释放执行锁），在这个线程上跑 RSP 循环
  -> 收到 c/s：更新 PC/断点状态，回到循环顶部重新 uc_emu_start
```

好处：

- 符合现有不变量"engine 只属于它的宿主线程"，寄存器读写全在同一个线程里做。
- all-stop 免费：执行锁没释放，其它 guest 线程本来也跑不了。
- 不需要"stub 线程 → engine 命令队列"这种双向协议。

代价与约束：

- 一个包处理期间所有 guest 线程都不动（all-stop 语义，正确）。
- 停住期间要处理的异常路径变多：客户端断线、`D` detach、runner 取消。
  统一走一个 `resume(ResumeAction)`，保证执行锁一定会被释放。
- **Ctrl-C 需要另开一个只读 socket 的小线程**：它只解析 `\x03`，置一个原子标志；
  停在循环里的线程看不到它（它不在读包），所以还要一个"运行期判停"的路径：
  原子标志 + 当前已装的地址 hook / 一个只覆盖当前 PC 的临时 code hook，
  命中就 `uc_emu_stop`。是否可靠见探针 P8。

### 3.3 停机点只在 `run()` 返回的边界

现在 `handleRunOutcome` 对主线程有一条断言：

```
guest stopped outside the return trap: pc=0x... err=...
```

debug stop 恰好就是"我们让它停在 return trap 之外"。所以集成点是：

```
run() 返回
  if (debug_controller->onRunStopped(thread, pc)) {   // 新增，最先判断
      debug_controller->serveWhileStopped(thread);    // park + RSP 循环
      continue;                                       // 重新进入 run()
  }
  // 原有 SVC / exit / fault / return-trap 处理
```

其它 guest 线程的 `until == 0`，天然可以从同一 PC 重入 `run()`，不需要额外处理。

**嵌套 guest 帧里的断点不做。** `dlopen` 构造器、JNI 回调、`pthread_once`
都会嵌套 `call_guest`（硬上限 32 层），在那种帧里停住意味着要保持 C++ 栈
不展开，还要让 `uc_emu_stop` 穿透到最内层 `uc_emu_start`。M9 的规则：

- 断点命中时如果 `debug_controller` 判断当前处于嵌套帧（backend 里已有
  嵌套层计数/`inHookCallback` 类似的上下文），直接 `E` 回复并写日志，
  **不让它停**；
- 客户端看起来就是"这个断点没生效"，文档里写明原因。

### 3.4 单步：给 `UnicornEngine::run` 加 count

`uc_emu_start(uc, begin, until, timeout, count)` 的第四个参数现在是硬编码 `0`：

```cpp
outcome.err = uc_emu_start(engine_, begin.value(), until.value(), timeout_us, 0);
```

改成：

```cpp
Result<RunOutcome> run(GuestVA begin, GuestVA until, uint64_t timeout_us, size_t count = 0);
```

单步 = `run(pc, 0, 0, 1)`。这是唯一不装 per-instruction hook 的单步方式；
`until = pc + 4` 在分支上不成立（会跑到 `until` 之外）。

### 3.5 断点 = 现有地址 hook

`addAddressHook` 已经满足全部要求：广播到所有 engine（含之后 `clone` 出来的），
`UC_HOOK_CODE(begin = end = address)` 只影响覆盖该地址的 TB，不会把整个模块
打成单指令。所以 Z0 是**低成本**的，和 M8 全区间 trace hook 完全不是一回事。

`HookContext` 已加 `requestStop()`（同线程 `uc_emu_stop`）。Probe 12A 确认它
停在**指令执行之前**：PC 等于断点地址，被 hook 的指令没有执行。所以 Z0 不需要
回退 PC，也不需要改写代码。

**但 TB 缓存必须手动失效**：后加的地址 hook 不会插进已翻译的 TB，断点会静默
不命中。`addStopHook` 成功后要失效该地址所在页（见 §6.2）。

### 3.6 thunk 断点是本项目相对真机 gdb 的增量

逆向工具用户的第一动作通常是在 import 上下断点：`JNIEnv::NewStringUTF`、
`open`、`memcpy`。这些地址在 thunk 页：

```
ThunkTable::base() == 0x70000000
第 i 项：0x70000000 + 8 * i   ->  svc #(0x8000 | i) ; ret
范围：  [base, base + 8 * count())
名字：  ThunkTable::nameOf(i)
```

没有 guest 指令，Z0 永远不会命中。处理方式：

- `Z0/z0` 的地址落在 thunk 范围内 → 不进 `addAddressHook`，记到
  `DebugController` 的 thunk 断点表；
- SVC dispatcher 在调用宿主 stub **之前**查表，命中则 park；
- stop reply 的 `name` 字段用 `nameOf(index)`（与 `bl.log` 的符号化是同一份数据）。

这条要作为验收项：BN 里在 `JNIEnv::NewStringUTF` 上断点必须能停。

**不做**：客户端如果绕过 `Z0`、直接用 `M` 往代码页写 `BRK`，v1 不支持
（Unicorn 会报 `UC_ERR_EXCEPTION`，我们只把它当 fault，不识别成断点）。
Z0 是唯一断点路径，文档写明。

### 3.7 watchpoint

`Z2/Z3/Z4`（写/读/访问）→ `UnicornBackend::addWatchpoint(kind, address, size)`：

- 和地址 hook 一样广播到所有 engine；
- 回调里判断 `[address, address + size)` 是否与区间相交，命中则 park；
- 只在存在 watchpoint 时才装 mem hook，不装不留开销；
- 粒度是"指令级别命中"，不是字节精确；同一指令同时读写会报一次。

### 3.8 模块基址：确定性是现成的，缺的是一个列表接口

`AddressSpace::next_free_ = 0x40000000` 起 bump 分配 → 同一目标、同一加载顺序，
模块基址跨进程一致。BN 必须知道这个基址才能对上符号。

- 门面现在只有 `moduleRange(handle)`，没有模块列表；`ModuleRegistry::modules()`
  有（`Module{path, base, span, is_virtual}`），门面不暴露。
- M9 给 `RuntimeInstance` 加一个只读视图 `moduleList()`，供 `qXfer:libraries:read`
  返回简单 XML：

```xml
<library-list>
  <library name="/data/app/libszstone.so"><section address="0x40001000"/></library>
  ...
</library-list>
```

- **不做 `qXfer:libraries-svr4`**：它要读 guest 的 `link_map`/`r_debug`，
  而 loader 目前没有合成 `r_debug`。等谁真的需要再说。
- 兜底方案：如果 BN 不吃 `libraries:read`（探针 P9），就在 BN 里手动
  rebase 到 `0x40001000`——可接受，但要写进使用说明。

### 3.9 线程

- `qfThreadInfo` / `qsThreadInfo` ← `ThreadScheduler` 新增 `snapshotThreads()`
  （内部 `threads_` 已有，门面不暴露）。
- `Hg/Hc` 切当前线程；`qThreadExtraInfo` 用现成的 `threadStateName()`。
- **all-stop 下非当前线程的 `g` 是受限的**：那个线程停在自己的 park 点或 futex 上，
  它的 engine 是空闲的。可以读（探针 P6 要验证跨线程读 idle engine 是否安全），
  但 x0–x30 只保证是它最后一次 park 时的值；`PC` 用 `RuntimeThread::next_pc`。
  实在不确定就只报 `PC`，其余回零，文档写明。

`qSupported` 的回复（第一版）：

```text
PacketSize=4000;qXfer:features:read+;qXfer:libraries:read+;QStartNoAckMode+
```

`vCont?` → `vCont;c;s`。内存包单次上限按 `PacketSize` 截断。

### 4.2 寄存器布局

aarch64 core，34 个寄存器，`g` 包 = 31×8 + 8 + 8 + **4** = **268 字节**
→ 536 个 hex 字符，小端。**注意 cpsr 是 32 位**：按 8 字节回会在连接时报
`Remote 'g' packet reply is too long (expected 268 bytes, got 272 bytes)`
（P1 实测，见 §6）。

```text
x0..x30 (31) | sp | pc | cpsr(32 位，高 32 位补零)
```

对应 Unicorn：`UC_ARM64_REG_X0..X30`、`UC_ARM64_REG_SP`、`UC_ARM64_REG_PC`、
`UC_ARM64_REG_CPSR`。

`target.xml` 第一版只报 core（`org.gnu.gdb.aarch64.core`）；BN 是否接受
"没有 fpu/v regs" 的描述由探针 P2 决定，不接受再补 `org.gnu.gdb.aarch64.fpu`。

### 4.3 帧与错误

- `$<payload>#<2 hex checksum>`；`}` 转义；ack `+`/`-`（未进 no-ack 模式时）。
- 未知包 → 空回复（标准语义），不回 `E`。
- 访问未映射内存 → `E14`；未映射写 → `E14`；寄存器越界 → `E01`。
- 客户端断线：`serveWhileStopped` 返回 `Detach`，恢复执行到自然结束。

## 5. 代码结构

```
runtime/debug/
├── debug_target.hpp             # 窄接口：modules/threads/memory/stop hook
├── debug_server.{hpp,cpp}       # listen/accept、帧、包分派、断点表、park 协议
├── target_xml.{hpp,cpp}         # aarch64 core 描述
└── debug_stub.cpp               # ENABLE_DEBUG=OFF：API 可链接，返回 Unsupported
```

V1 把设计里的 `debug_controller` / `rsp_server` / `rsp_packets` 合并成
`debug_server`：三者共享同一份停机状态，拆开只会多一层转发。等 watchpoint
与模型 B 进来再拆。

`debug_target.hpp` 由 `RuntimeInstance::Impl` 实现，**门面只多一个方法**：

```cpp
Result<void> startDebugServer(const debug::Options &options);
```

不暴露 `getMemory()` / `getThreads()`，符合"门面就是门面"。

### 改动点

| 文件 | 改动 |
|---|---|
| `backend/unicorn/unicorn_engine.{hpp,cpp}` | `run()` 增 `count`；`stop()` 已存在 |
| `backend/unicorn/unicorn_backend.{hpp,cpp}` | `addWatchpoint/removeWatchpoint`（广播） |
| `observer/hook/hook_context.{hpp,cpp}` | `requestStop()` |
| `threads/scheduler.{hpp,cpp}` | debug stop → park → 重入；`snapshotThreads()` |
| `instance/runtime_instance.{hpp,cpp}` | `startDebugServer()`、`moduleList()` |
| `user_code/<case>/main.cpp` | `--debug [PORT]`（默认 31337；仅 DEBUG 构建生效） |
| `tests/CMakeLists.txt` | `09_*` gate（仅 `DUCKEMU_ENABLE_DEBUG=ON`） |

**构建（与 trace 同一形态）**：

```cmake
option(DUCKEMU_ENABLE_DEBUG "Build the GDB remote debug server (RSP)" OFF)

set(DUCKEMU_DEBUG_SOURCES)
if(DUCKEMU_ENABLE_DEBUG)
  list(APPEND DUCKEMU_DEBUG_SOURCES
    src/runtime/debug/debug_server.cpp
    src/runtime/debug/target_xml.cpp)
else()
  list(APPEND DUCKEMU_DEBUG_SOURCES src/runtime/debug/debug_stub.cpp)
endif()
```

- 默认 OFF：生产构建里没有 RSP 代码，`startDebugServer()` 走
  `debug_stub.cpp`，返回 `Unsupported`（"configure with
  -DDUCKEMU_ENABLE_DEBUG=ON"），调用方不需要 `#ifdef`。
- ON：编入协议栈；运行时仍要显式传 `--debug [PORT]`（默认 31337）才创建监听，
  只绑 `127.0.0.1`。两层开关都要过。
- 不引入新依赖（不用 capstone，不用额外库），所以 DEBUG 和 TRACE 是两个独立开关。

- **状态**：`gdb_spike` 已实现（`code/tools/spike/gdb_spike.cpp`，target

3. **`swbreak+` 必须在 `qSupported` 里 advertise**，否则 stop reply 里的
   `swbreak:;` 会被当成协议错误（"Unexpected swbreak stop reason"），
   随后客户端认为线程还在运行。`hwbreak+` 同理。
4. `qSupported` 里的 `xmlRegisters=i386` 与 `set architecture aarch64` 无关，
   是 gdb 自己的 XML 寄存器集合声明，stub 忽略即可。
5. `Hc<tid>` 在 gdb 里既会出现 `Hc-1`（全部）也会出现 `Hc0`/`Hc1`；
   `H` 一律回 `OK`。
6. 线程查询是 `qfThreadInfo`/`qsThreadInfo` 交替，一次会话出现 7 次，正常。
7. `qXfer:features:read` 被请求两次（连接时、断点命中后各一次），
   分块大小按 `0,1000` 给，回复必须正确区分 `m`/`l`。

BN 的 adapter 大概率是 LLDB 血统（会发 `qHostInfo`、`qProcessInfo`、
`jThreadsInfo`、`qMemoryRegionInfo` 等）。stub 对这些未知包统一回空包，
日志里能看到真实集合；P1 的 BN 半就是拿这份日志替换上面的序列。

#### 6.2 libeleven 垂直切片（已通，2026-11-01）

正式实现已经能接真实目标（先用 gdb 验证；BN 用同一组包）：

```bash
cmake -S code -B build-dbg -G Ninja -DCMAKE_BUILD_TYPE=Release -DDUCKEMU_ENABLE_DEBUG=ON
cmake --build build-dbg --target duckemu_libeleven_case -j
./build-dbg/user_code/duckemu_libeleven_case --debug          # 默认端口 31337
./build-dbg/user_code/duckemu_libeleven_case --debug --debug-port 2345
```

已验证（gdb）：

- 连接后停在入口 `0x6022ccb4`（`sub sp, sp, #0x1c0`），寄存器/内存可读；
- `stepi` 逐条：`ccb4 -> ccb8 -> ccbc -> ccc0`；
- `break *0x6022cdb4` + `continue` 命中，`pc == 0x6022cdb4`；
- `detach` 后目标继续跑完，`data(1)` 正常输出。

**这条路径踩出的两个 Unicorn 事实（比协议更重要）**：

1. **code hook 里 `requestStop()` 停在指令之前**（Probe 12A：PC == 断点地址，
   被 hook 的指令没有执行）。所以 Z0 直接用地址 hook，不需要 PC 回退，
   也不需要写 `BRK`。
2. **`BRK #0` 在 Unicorn 里不可用**（Probe 12B）：不返回
   `UC_ERR_EXCEPTION`，只触发 `UC_HOOK_INTR`（intno 7），PC 卡在 BRK 上
   反复重试（1000 次预算打满）。软断点（改内存写 BRK）这条路彻底排除。
3. **TB 缓存会吞掉 count 与后加的 hook**：
   - `uc_emu_start(count>0)` 才安装计数 hook，且**不 flush TB**（`uc.c:1202`）。
     上一轮 `count=0` 翻译过的 TB 会被复用，计数不生效——单步从入口一直跑到
     函数末尾（实测 `0x6022ccb4 -> 0x6022b3b4`）。
     修复：计数运行前 `invalidateCode(pc, 4)`。
   - 后加的地址 hook 也不会插进已翻译的 TB，断点静默不命中。
     修复：`addStopHook` 成功后让 backend 失效该地址所在页。

这两条都写进了代码注释，gate 里要有对应的回归用例。

### P2：只报 core 的 `target.xml` 够不够

- **问题**：BN 是否接受只有 `org.gnu.gdb.aarch64.core` 的描述。
- **方法**：P1 的 stub 只给 core；若报错，再补 `fpu`/`sve` 观察差异。
- **判据**：寄存器视图出现 x0–x30/sp/pc/cpsr，无 warning；断点/单步正常。
- **记录**：BN 的 Debugger 控制台输出原文。

### P3：BN 的断点走 `Z0` 还是写 `BRK`

- **问题**：客户端自己改内存还是发 `Z0`。这决定要不要支持 `BRK` 识别。
- **方法**：P1 stub 的日志看是否出现 `M` 写到代码页；或只接受 Z0 时断点是否仍生效。
- **判据**：确定唯一路径；若 BN 走 `M`，把"支持 `M` 写 `BRK`"提进范围。
- **记录**：包日志。

### P4：`count = 1` 恰好一条指令

- **问题**：`uc_emu_start(..., count=1)` 在 `svc`、`bl`、`br`、`ret`、`ldxr` 上是否
  只前进一条。
- **方法**：`unicorn_spike` Probe 12C/12D/12E：无 hook、hook 在第二条、hook 在起点。
- **判据**：PC 严格前进一条指令；hook 不改变计数语义。
- **状态：通过（2026-11-01）**。12C（无 hook）和 12E（hook 正好在起点）都是
  一条指令；12D（hook 在第二条，count=2）是两条。
- **但**：真实目标上第一次单步跳到了函数末尾——不是 count 语义，而是 TB 缓存
  （`uc.c:1202` 装计数 hook 时不 flush）。修法是计数运行前失效当前页。
  见 §6.2 第 3 条。

### P4b：`BRK` 与停点语义

- **问题**：软件断点（改写指令为 `BRK #0`）是否可行；hook 停点在哪。
- **方法**：Probe 12A/12B。
- **状态：已定**：12A → hook 里 `uc_emu_stop` 停在指令执行前（PC == bp，
  指令未执行）；12B → `BRK #0` 只触发 `UC_HOOK_INTR`（intno 7）并卡在 BRK
  反复重试，Unicorn 不消费该异常。**软断点路径排除，Z0 只用地址 hook。**

### P5：停住的 guest 线程持锁跑 RSP 循环，其它线程冻结且能恢复

- **问题**：park 在 `hostThreadLoop` 里、不释放 `execution_mutex_`，
  其它 runnable/blocked 线程是否彻底不动；continue 后是否从同一 PC 正确续跑。
- **方法**：`unicorn_spike` Probe 13 或用 `03_pthread_join` 改造：主线程 park，
  另一线程跑一个递增计数器；park 期间计数不变；continue 后继续。
- **判据**：park 期间计数冻结；继续后无指令重复、无 `svc+4` 停错。
- **记录**：计数器值与 PC。

### P6：跨线程读空闲 engine 的寄存器

- **问题**：all-stop 下 `Hg<tid>` 后读另一个线程的寄存器（它的 engine 空闲），
  是否安全、值是否有意义。
- **方法**：两个线程各跑一段设置 x0 的代码，主线程 park；从主线程读另一 engine
  的 x0/PC。重复 10000 次看是否崩溃或读脏。
- **判据**：不崩溃、值稳定；若不稳定 → 只报 `PC`（`next_pc`），其余回零。
- **记录**：结论 + BN 中非当前线程寄存器视图的表现。

### P7：单地址 code hook 的 TB 粒度开销

- **问题**：`UC_HOOK_CODE(begin = end = addr)` 是否只影响该地址附近，
  而不是把整个模块打碎成单指令 TB。
- **方法**：同一个真实目标（szstone 或 dy7）跑三次：无 hook / 1 个断点 /
  M8 全区间 trace hook；各测 5 次取中位数。
- **判据**：1 个断点的额外耗时 < 5%；全区间 hook 的差距作为对照。
- **记录**：三次耗时。

### P8：跨线程 `uc_emu_stop` 的可靠性（Ctrl-C 路径）

- **问题**：A 线程对 B 线程的 engine 调 `uc_emu_stop`，是否像 `_timeout_fn`
  一样有竞态（M3 已踩过 `emulation_done` 非原子）。
- **方法**：`unicorn_spike` Probe 14：B 跑长循环，A 在随机延迟后 `stop()`；
  检查 B 的停点 PC 是否是完整指令边界（不是 `svc+4`、不是半条）。
- **判据**：1000 次 0 次停错；否则 Ctrl-C 改为"原子标志 + 当前 PC 临时 code hook
  判停"（hook 已在，成本仅为一次比较）。
- **记录**：成功率、失败样本 PC。

### P9：BN 对 `qXfer:libraries:read` 的反应

- **问题**：BN 是否用这个包自动摆正模块基址。
- **方法**：P1 stub 返回一个 `<library-list>`，名字对上一个本地文件；
  在 BN 里打开同名 `.so`，看 Debugger 是否自动 rebase、符号是否解析。
- **判据**：BN 的 Modules 视图出现该模块且地址 = XML 里给的地址；
  若不吃，确认 rebase 兜底可行。
- **记录**：BN 视图截图/地址。

### P10（可选，不设 gate）：IDA Remote GDB 连 aarch64

- **问题**：同一 stub 能否被 IDA 9.x 的 Remote GDB 接受。
- **方法**：IDA `Debugger → Switch debugger → Remote GDB`，处理器选 ARM。
- **判据**：能连上并读到寄存器就算通过；报错不影响 M9 范围。

| Gate | 内容 |
|---|---|
| `rsp_packets_test` | 帧/checksum/转义、分包 `qXfer` offset、`g/G` 268 字节布局、`E` 回复、未知包空回复 |

## 8. 风险与限制（写进使用说明）

1. **只支持模型 A**：不能在目标运行到一半时踩停；默认构建没有调试面，
   `DUCKEMU_ENABLE_DEBUG=ON` 且传 `--debug` 才有。
2. **没有信号**：stop reason 只有 `SIGTRAP`；带信号继续（`Cxx`/`vCont;Cxx`）
   回 `E`；guest fault 只映射成 `SIGSEGV`/`SIGILL` 上报，不投递。
3. **没有 DWARF/CFI**：BN 里只有反汇编；调用栈要靠 x29 链，release so 可能只有一帧。
4. **嵌套帧断点不生效**（§3.3），日志会写原因。
5. **thunk 断点只覆盖 thunk 页**；syscall 本身（`svc #0` 的真 syscall）要想停，
   用 M8 的地址 hook 或以后加 `qRcmd monitor syscall`。
6. **性能**：断点只影响该地址的 TB；watchpoint 装全局 mem hook，有 watchpoint 时才有开销。
7. **安全**：RSP 无认证。默认构建不含 RSP 代码；启用后只绑 `127.0.0.1`、
   只在显式 `--debug` 时监听，绝不通过 Worker/System 暴露——它给的是任意
   寄存器/内存写。
8. **BN 一次性连接**：目标返回后端口关闭，下一次调用要重新连（模型 A 的固有形态）。
